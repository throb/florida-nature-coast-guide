OpenClaw Daily Update Instructions

Use this file as the daily operating prompt for OpenClaw. In production, OpenClaw is remote from Vercel, so it must publish over HTTPS to the deployed site. Do not use localhost except for local testing.

Goal

Update Nature Coast Insider daily with fresh, source-backed local guide data: images, weather/context settings, places, day trips, weekly issue content, source candidates, and source metadata.

Production Endpoint

POST https://<VERCEL_DOMAIN>/api/publish
Authorization: Bearer <PUBLISH_API_KEY>
Content-Type: application/json

The publish secret must come from OpenClaw's secure environment. Never write it into a repo file, prompt transcript, or public artifact.

Daily Checklist

  1. Fetch the current public payload from GET https://<VERCEL_DOMAIN>/api/city-pulse?city=nature-coast.
  2. Check official sources first: city/county calendars, parks, tourism boards, chambers, direct venue pages, FWC, NWS/weather sources.
  3. Update only rows/settings that changed. Stable slugs make publishes idempotent.
  4. Use draft or review for AI-generated or unapproved editorial picks.
  5. Use published only for content that should appear publicly.
  6. Classify source candidates before publishing. Only raw.kind: "event" candidates belong in Community Events; rules, closures, access notes, weather, and advisories belong in Conditions or planning-note surfaces.
  7. For event candidates, never use a generic events/calendar index as the clickable URL. Find the exact event detail page or keep the candidate in draft with a note explaining what is missing.
  8. For businesses and places, prefer the official business/site/menu/booking URL as the public click. Use tourism or chamber directory pages as source evidence or backup, not the primary link, when a better canonical destination exists.
  9. Publish found images as stable public URLs, or publish generated images as images[].dataBase64 so the API can store them in Supabase Storage.
  10. Publish weather/context updates under settings.weatherLocations or settings.weatherSnapshot.
  11. Publish the daily This Week hero through the image API target setting:homepage. See the Daily Hero Image API section below.
  12. After publishing, fetch /api/city-pulse again and verify the changed values are present.

Daily Hero Image API

The main This Week masthead image is controlled by settings.homepage.image. OpenClaw should refresh it during the daily 3am update when a better current image is available. The site will use this published image first; if none exists, the browser falls back to its local daily image pool.

  • Use target.type: "setting" with target.key: "homepage".
  • Use url for a stable public direct image URL from Pexels, Wikimedia, official sources, or another usable provider.
  • Use dataBase64 for a generated image. The publish API uploads it to Supabase Storage and writes the resulting public URL into settings.homepage.image.
  • Include imageLabel, imageCredit, and updatedAt in target.value so the page caption and audit trail stay useful.
  • After publish, verify GET /api/city-pulse?city=nature-coast returns homepage.image, homepage.imageLabel, and homepage.imageCredit.

Local Daily Command

For the 3am daily update, run the masthead publish as its own step after weather/source checks. The helper loads the project .env, searches Wikimedia Commons using a date-rotated set of regional themes, filters for useful landscape photos, publishes the selected image through /api/publish, then verifies /api/city-pulse. If Commons is unavailable, it falls back to the curated local pool. 

npm run publish:masthead -- --direct

Use --dry-run --direct first during local testing. Use --fallback-only to force the curated pool, --query "Crystal River manatee" to steer a specific day, and --endpoint https://<VERCEL_DOMAIN>/api/publish for production once the deployed API is live.

Event Candidate Research Rules

Event cards must be useful when clicked. A candidate is not review-ready unless raw.kind is event and its url opens the exact event, festival, or detail page that supports the title and summary.

  • Do not set review/published event candidates to generic pages such as /events/, /calendar, /Calendar.aspx, or chamber search result pages.
  • Do not put alerts, rules, closures, water restrictions, access notes, weather advisories, or season/regulation notices in Community Events. Use raw.kind values such as alert, rule, or access-note and publish them to conditions/planning-note surfaces instead.
  • Search the event title, venue, city, and date until you find the direct event URL. Prefer official city, venue, chamber detail, tourism detail, or event-owned sites over scraped aggregator pages.
  • If a tourism calendar lists the event but has a separate detail URL, use that detail URL, not the calendar index.
  • If an official event site exists, use it as the primary URL when it is useful. Keep the tourism/city detail URL in raw.backupUrl when it has clearer date/time/location facts.
  • Extract enough information to help the user decide: date, time, venue/address, cost if available, contact/organizer, important rules, schedule highlights, and source notes.
  • Set raw.linkQuality to exact only after the URL is verified to be a detail page for that specific event. Review/published candidates without exact links are rejected by the publish API.
  • When exact research fails, keep the item as draft, set raw.linkQuality to needs-detail, include the generic source in raw.sourceUrl, and do not show it as a review pick.

Place & Business Link Rules

Place and business links should send users to the best action page, not merely to the page where OpenClaw found the lead. Tourism, chamber, and directory pages are useful evidence, but they are often not the best public click.

  • For restaurants, outfitters, guides, marinas, hotels, shops, and venues, search for the business-owned website first.
  • If a directory page links to the official site, follow that link and inspect the official site.
  • Use the official website, menu/order page, reservation/booking page, ticket page, or official social page as web, href, or public_url when it is live and useful.
  • Keep the tourism/chamber/directory page in sourceUrl, backupUrl, or raw.sourceUrl when it verifies address, category, hours, or local context.
  • If the official site is broken, thin, stale, or less useful than a direct action page, choose the more helpful URL and document why.
  • Before publishing, click the public URL and verify it lands on the expected business/place/action.

Eats Photo Identity Rules

A place photo is not fixed just because a card loads /api/place-photo. OpenClaw must prove the image belongs to the actual restaurant, bar, bakery, coffee shop, or stop.

  • For API-driven Eats updates, publish the page data through settings.guidePages.eats. The Eats page reads that live setting after loading its bundled fallback data.
  • Prefer an exact googlePlaceId or placeId for every Eats card. Use placePhotoQuery only as fallback discovery text.
  • Call /api/place-photo?format=json&placeId=<id> and confirm the returned place.name, place.address, or place.googleMapsUri matches the intended business.
  • Browser-render the public Eats page and visually reject generic scenery, repeated fallback images, unrelated water/tree/street shots, tourism filler, or another business.
  • If the exact Google Place ID still returns a bad first photo, publish a reviewed image from the business-owned site/social/source when allowed, or mark photoStatus as BLOCKED needs human image.
  • Verification must be per place: PASS exact place photo, PASS reviewed fallback, or BLOCKED needs human image. DOM counts and HTTP 200 checks are not enough.
  • Do not download/rehost Google Places, Google Maps, or copyrighted business/social photos into site storage. Durable Eats images must be app-owned or rights-cleared: advertiser/business-provided, user-submitted with permission, generated, public-domain/compatible-license, or paid/licensed stock.
  • For approved non-Google image URLs, run npm run import:image -- --url "<approved-image-url>" --id "<place-slug>" --label "<place name>" --credit "<credit>", then publish the returned storage URL in settings.guidePages.eats.

Rules

  • Do not publish unsourced facts as final public content.
  • Do not hard-delete historical content; archive instead.
  • Do not overwrite approved public content with AI-only guesses.
  • Do not use social posts as authoritative sources; use them as leads.
  • Keep image URLs stable and publicly accessible. For generated images, use the API upload path instead of Vercel filesystem writes.

Advertiser Copy Rules

  • Do not use founder, founding, founding sponsor, or founder rate in advertiser, sponsor, or partner copy.
  • Use community-oriented language instead: community partner, community partnership, community partner slot, or local guide partner.
  • Position advertisers as part of the community-building team that helps keep the guide useful, source-backed, and connected to real local businesses.
  • Keep sponsor labeling clear and honest. Paid placements should still be labeled as sponsor/partner content where relevant.
